<objective>
Make the watchlist a real, rule-enforced resource: readable with live price, open price,
change-from-open and up to 60 sparkline points; addable through the one shared ticker rule
and registered with the running market source; removable — rejected 409 when a position is
held and 404 when the ticker was never watched.

Purpose: the watchlist is the durable record that every position has a live price feed.
`03-01` proved the router-to-service-to-`run_db` seam on the trade path; this plan expands
that same seam sideways onto the second resource, and publishes the `add` / `remove`
functions the ROADMAP records as a contract Phase 6 must route through. Every rule lands
behind the seam so the LLM path cannot bypass what a manual request is held to.

Output: `app/services/watchlist.py` with the three seam functions and the one null rule;
`app/api/watchlist.py` with the three routes; `main.py` wired with the router above the
static mount; a `RecordingSource` fake and two test modules covering the read, add and
remove behaviors including the ordering, idempotency and concurrency edges.
</objective>

Define `def quote(cache: PriceCache, ticker: str) -> TickerQuote` — the single place D-15's null rule lives. `update = cache.get(ticker)`. When it is `None`, return `TickerQuote(ticker, None, None, None, [])`. Define `async def read_watchlist(db_path: Path, cache: PriceCache) -> list[TickerQuote]`: `rows = await run_db(db_path, get_watchlist)`, then one `quote(cache, row["ticker"])` per row, in the order the rows arrive. `get_watchlist` already orders ascending by ticker, so this function imposes no ordering of its own. Define `async def add(db_path: Path, source: MarketDataSource, ticker: str) -> WatchlistEntry` with the parameter list approved at `03-01` Task 1. Body, in this exact order: `symbol = normalize_ticker(ticker)` first, so a malformed symbol raises plain `ValueError` — translated to 400 by the handlers `03-01` registered — before any I/O; then `added = await run_db(db_path, _add_row, symbol)`; then `await source.add_ticker(symbol)`; then `logger.info("Watchlist: added ticker %s", symbol)` using lazy `%s` formatting; return `WatchlistEntry(symbol, added)`. The database write comes first and the source registration second (D-09): the watchlist row is the durable record and the source is restarted from it on every boot, so a failed registration self-heals on the next start, whereas an orphaned feed would not. Do not wrap the registration in a rollback or a retry — that is defensive machinery for a failure the simulator cannot realistically produce. Adding an already-watched ticker is a success, not an error: `add_watchlist_ticker` no-ops on conflict and reports `added` as `False`, and re-registering with the source is a harmless no-op that repairs a ticker whose earlier registration failed.

Define `def _add_row(conn: sqlite3.Connection, ticker: str) -> bool` — a plain `def` taking the connection first, wrapping `return add_watchlist_ticker(conn, ticker)` in `with writing(conn):` so every write in this phase goes through one `BEGIN IMMEDIATE` shape rather than relying on the connection's autocommit mode.

Define `async def remove(db_path: Path, ticker: str) -> None`: `symbol = normalize_ticker(ticker)`, then `await run_db(db_path, _remove_checked, symbol)`, then `logger.info("Watchlist: removed ticker %s", symbol)`. It does not touch the market source: the simulator keeps producing a price for an unwatched ticker until the process restarts, which is harmless because the source is started from the watchlist rows on every boot and the client renders from this API, not from the stream's key set. `MarketDataSource.remove_ticker` therefore stays unused in Phase 3, deliberately.

## Flagged assumptions (unresolved probe items)

The edge probe surfaced 12 rows against this plan's requirements. Nine are authored into
`must_haves.truths` with their `(requirement category)` tag. The remaining three arrived
`unclassified` and are recorded here rather than dropped; each stays `unresolved` and carries
a planner reading the executor implements and a reviewer should confirm.

- **WATCH-02 — unclassified.** "Add validated by the shared rule after uppercasing, rejected
  400 otherwise" produced no edge category the probe could classify. Planner's reading:
  *the shared rule* means calling `normalize_ticker` from `app.market`, never a second regex,
  and *after uppercasing* means the normalized form is what is stored, what the response
  names, and what a later removal must match — so `add("pypl")` produces a `PYPL` row and a
  response naming `PYPL`. The 400 arrives through the bare-`ValueError` handler `03-01`
  registered, not through a Pydantic constraint, which would return 422.
- **WATCH-03 — unclassified.** "Adding registers the ticker with the live source so it starts
  producing prices" produced no classifiable edge. Planner's reading: registration is
  `await source.add_ticker(symbol)` **after** the committed database write (D-09), and
  "starts producing prices" is proven two ways — a `RecordingSource` asserting the call is
  made and its ordering relative to the row, and one test against a really-started
  `SimulatorDataSource` asserting a price actually appears in the cache. A fake alone would
  prove only that a method was called.
- **WATCH-06 — unclassified.** "Removing a ticker that is not on the watchlist returns a 404"
  produced no classifiable edge. Planner's reading: 404 is the answer for a **well-formed**
  symbol that names no watchlist row. A malformed symbol is a 400 from the shared ticker rule,
  raised before any lookup, because it cannot name a row at all; and a well-formed symbol
  whose position is held is a 409, checked before the delete. So the DELETE surface is
  400 → 409 → 404 → 204, in that decision order.
