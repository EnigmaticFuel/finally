<objective>
Close the one missing seam in this phase, seen from both directions: nothing reconciles the
market data source's ticker set with the tickers the user actually cares about.

Forward direction (G-01): `execute_trade` registers the traded symbol with the running feed
before it waits for a price, so trading a ticker the source has never heard of actually fills
and joins the watchlist. Backward direction (G-02): the lifespan starts the feed from the
persisted watchlist rather than from a hardcoded constant, so a ticker the user added in an
earlier run still prices after a restart.

Purpose: PORT-07 and ROADMAP SC2 are currently unreachable in production — the 2s price wait
always expires for an unregistered symbol — and a user-added ticker becomes a stranded holding
after any restart: null price, silently excluded from `total_value`, unsellable (400),
unremovable (409). Both are the same absent registration seam. The phase goal, "the user's
positions and watched tickers are real and live-valued," fails on both.

Output: `execute_trade` amended to the contract shape locked in `03-SEAM-CONTRACT.md`'s
Amendment section; `startup_tickers` published from the watchlist service and wired into the
lifespan; every call site moved; the cache-pre-seeding fixture demoted so it can no longer
stand in for the registration step; and two production-shaped tests in a new
`backend/tests/test_feed_reconciliation.py` that drive the real lifespan and the real
`SimulatorDataSource` with no hand-written prices at all.
</objective>

<planner_probe_findings>
Two short probes were run against the current tree before this plan was written, so the
executor does not have to discover the mechanism. Both are reproducible from `backend/`.

**Probe A — registration primes the cache synchronously.** With a started
`SimulatorDataSource`, `await source.add_ticker("PYPL")` followed immediately by
`wait_for_price(cache, "PYPL", timeout=2.0)` returned a price in **0.0000s** with 60 history
points already seeded. `SimulatorDataSource.add_ticker` calls `_seed()` (`simulator.py:266`,
`:280-288`) inside the await, so the first tick is already in the cache when `add_ticker`
returns. Consequence for the executor: the fix needs no sleep, no retry and no polling of its
own, the new tests are fast and deterministic, and **no elapsed-duration assertion should be
written** — this repo already carries one timer-granularity flake on Windows.

**Probe B — an unstarted source is an inert no-op.** `SimulatorDataSource.add_ticker` returns
at `simulator.py:261-262` when `start()` has not run, leaving the cache untouched (probe read
back `None`). Consequence: the existing route-level tests in `backend/tests/api/test_portfolio.py`,
which prime the cache by hand against an app whose lifespan never runs, keep passing unchanged
after this plan — the new registration call is inert for them. That file is deliberately not in
this plan's `files_modified`.

**Probe C — G-01 reproduced end-to-end.** A real app under `with TestClient(app) as client:`
(which runs the real lifespan), trading `PYPL`:
`400 {"detail":"No price available for PYPL yet, please try again"}` after **2.06s**, and PYPL
absent from `GET /api/watchlist`. Trading the same symbol *after* a `POST /api/watchlist` — the
one path that does register — filled at 200.

**Probe D — G-02 reproduced end-to-end.** After exiting that lifespan and building a second app
against the same `db_path`, the source tracked only the ten defaults; `GET /api/watchlist`
reported `PYPL` with `price: None`; `GET /api/portfolio` reported the held position with
`current_price: None`, `market_value: None` and a `total_value` of 9662.91 that excluded it;
`POST /api/portfolio/trade` sell returned 400 with the same no-price message; and
`DELETE /api/watchlist/PYPL` returned 409. The stranded holding is exactly as described.

**Mechanism confirmed for the new tests:** `with TestClient(app) as client:` drives the real
lifespan (startup and shutdown) with the real simulator, and a second `create_app()` pointed at
the same `db_path` is a genuine restart. `ensure_initialized` memoizes per resolved path, so the
second app reuses the initialized database rather than re-seeding it. Nothing about the
mechanism is uncertain.
