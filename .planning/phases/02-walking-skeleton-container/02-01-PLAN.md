<planner_decisions>
Three implementation choices delegated to the planner by CONTEXT.md "Claude's Discretion", recorded here with their reasons so the executor does not re-litigate them:

1. **Image tag `finally-app:latest`, container name `finally-app`.** An image called `finally:latest` already exists on this machine, built 2026-08-04 with the flattened `/app` layout D-05 forbids and `CMD ["uvicorn","app.main:app",...]`, which cannot boot because `backend/app/main.py` exposes only `create_app()`. D-10's build-if-missing policy would find that image, skip the build and start a container that dies. A distinct tag removes the collision at zero cost; D-10's build-timestamp print (plan `02-02`) stays as the general mitigation. Do not delete or overwrite `finally:latest`.

2. **Publish as `-p 127.0.0.1:8000:8000`, not `-p 8000:8000`.** Docker's default publish binds `0.0.0.0`, putting the terminal on the LAN. This is a localhost single-operator app with no auth, Playwright runs on the host, and PLAN.md section 11 is "a strong guide, not a binding contract" per PROJECT.md Key Decisions. Loopback-only publishing costs nothing and closes T-2-04.

3. **`uvicorn --factory app.main:create_app` with an explicit `--workers 1`, exec-form CMD.** `--factory` is mandatory, not stylistic - research ran `uvicorn app.main:app` against the live tree and got `Error loading ASGI app. Attribute "app" not found in module "app.main"`. `--workers 1` is redundant to uvicorn's default of one process, and that is the point: DOCK-06's `[CORR]` asks for a guarantee that is inspectable from outside, not an invisible default. Exec form keeps uvicorn as PID 1 so `docker stop` delivers SIGTERM and the lifespan teardown calling `source.stop()` actually runs.

**Windows execution note (not a code change).** Every `docker run -v` in this plan's verify commands is run from Git Bash on Windows, where MSYS rewrites the container-side `/app/db` into a Windows path. Prefix those commands with `MSYS_NO_PATHCONV=1` and use `$(pwd -W)` for the host half. The committed `start_mac.sh` (plan `02-02`) targets macOS/Linux and carries neither - adding them there would be defensive programming for a platform the script does not serve.

`MSYS_NO_PATHCONV=1` is a property of **invoking** a POSIX command line from Git Bash, not a property of any script. It is an environment variable read by the MSYS runtime when it spawns a native Windows executable, so prefixing an invocation (`MSYS_NO_PATHCONV=1 bash scripts/start_mac.sh`) suppresses the rewrite for that process and its children without putting one byte of Windows handling inside the file being run. This distinction is what lets plan `02-02` exercise the `.sh` pair at runtime on this machine while keeping the committed script Windows-free, and it must not be read as a licence to add the prefix, `$(pwd -W)`, or any other MSYS accommodation to `scripts/start_mac.sh` or `scripts/stop_mac.sh`.
</planner_decisions>
