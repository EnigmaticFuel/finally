<objective>
Deliberately stress SQLite WAL over the Windows Docker Desktop bind mount of a OneDrive-synced path, and turn the result into recorded evidence plus a re-runnable regression guard.

Purpose: the ROADMAP flags this as the phase's one genuinely unconfirmed variable, and D-16 requires it be stressed here rather than left to surface later. Phase 1's concurrency suite passed against a host-filesystem database; the bind mount is the untested layer. Driving contention here means a `database is locked` failure is diagnosed as an infrastructure fact now, instead of being discovered under Phase 3's trade logic where it would look like a trade bug.

**What research already measured, and why the task is still worth writing.** The probe was run three ways on this machine during research: `PRAGMA journal_mode=WAL` returned `wal` with both sidecars created; six threads times forty `BEGIN IMMEDIATE` increments produced 240/240 committed with zero errors in 1.18s; and a host-native Windows writer racing a container writer produced 300/300 with `PRAGMA integrity_check` returning `ok`. D-16's flagged risk did not materialise. The task remains because a measurement taken in a throwaway directory is not the same as a measurement taken against `db/`, and because a committed script is a regression guard that a research session is not.

Output: `scripts/wal_stress.py`, an appended `.gitignore` rule, and a recorded measurement.

Decisions this plan implements: D-16 (stress WAL over the bind mount deliberately, in this phase, and diagnose in place if it fires).
</objective>

`assert_journal_mode_is_wal(path)` - open a connection with `isolation_level=None`, execute `PRAGMA journal_mode=WAL` and **fetch and check the returned row**. This is the assertion that must run first, before any contention is driven. The pragma returns the *resulting* mode, and if the change could not be applied it returns the *original* mode instead - so a silent downgrade to `delete` produces no exception and no log line. Phase 1's `connection.py` executes this pragma and discards the return value, which means a silent downgrade is invisible to the application today. Fail with a message naming the mode that was actually returned. **This is a diagnostic gap in Phase 1 code, and `backend/app/db/connection.py` is frozen by this phase's scope - do not edit it. `run_writers(path, ...)` - the contention driver, structured on the analog: module-level `SCREAMING_SNAKE_CASE` tunables rather than magic numbers, a `_run(targets)` helper that starts every thread then joins every thread, and a writer closure that performs a read-modify-write inside an explicit `BEGIN IMMEDIATE` transaction, appending to a `commits` list on success and to an `errors` list on failure. Calibrate against the research measurements so a regression is legible: six writer threads times forty increments, matching the 240/240 probe. Set `busy_timeout` to the same 5000 ms the application uses, so a timeout here means the same thing it would mean in production.

**The schema is fixed, because Task 2 reads it back from a second container.** The scratch database holds exactly one table, `counter`, with columns `id INTEGER PRIMARY KEY` and `value INTEGER`, seeded with the single row `id=1, value=0`. Every writer increments `value` on that row. Task 2's restart-persistence assertion re-reads `select value from counter where id = 1` from inside a freshly created container and compares it to the value this run reported, so the table name, the column name and the row id are contract rather than implementation detail - do not rename them.

`assert_no_lost_updates(path, ...)` - assert `errors` is empty, assert the commit count equals threads times increments, then reopen the database and assert the final stored value equals the starting value plus the increment times the number of committed writes. Quote the analog's doctrine in the docstring: the load-bearing assertion is not "no errors" - a design that silently loses updates raises nothing, and what catches it is the final stored value. Finish with `PRAGMA integrity_check` and require `ok`.

`main()` - create the scratch database fresh, run the three phases in order, then print exactly one result line. **Its format is pinned, because Task 2's automated gate greps it and a loose format makes that gate satisfiable by accident.** The line is space-separated `key=value` pairs, in this order and with these exact keys:

`journal_mode=<mode> commits=<n> expected=<n> actual=<n> errors=<n> integrity_check=<result> elapsed=<seconds>s`

So a healthy run prints `journal_mode=wal commits=240 expected=240 actual=240 errors=0 integrity_check=ok elapsed=1.18s`. The `key=value` shape matters specifically: the file path `wal_stress.db` is also printed by this script, so a gate looking for a bare mode token would match the path and pass without the pragma ever having returned the right mode. Task 2 greps `journal_mode=wal`, not a bare token, for that reason. No emojis in any printed string. On failure, print which of the four documented signatures matched - journal mode reading back `delete` means the filesystem refused WAL and shared memory is unavailable; `disk I/O error` or `SQLITE_IOERR_SHM` means the `-shm` mmap failed; `unable to open database file` means the directory is not writable or the path does not reach the mount; and `database is locked` *while the journal mode reads `wal`* is application-layer lock contention that outlived the busy timeout, not a mount problem at all. Naming the signature is what separates diagnosis from guessing, which is the project's root-cause-before-fixing rule applied to the one risk this phase was told to watch.
