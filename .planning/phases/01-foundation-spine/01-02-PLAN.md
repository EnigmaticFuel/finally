Create `backend/app/db/connection.py` with module constant `BUSY_TIMEOUT_MS = 5000` and four sections following the `# --- Section ---` convention: connecting, transactions, initialization, offload.

`connect(path)` is a `@contextmanager` yielding a `sqlite3.Connection` and closing it on exit (D-03). Open with `sqlite3.connect(path, isolation_level=None)` — this is mandatory, not stylistic: the stdlib default `isolation_level=''` is legacy implicit-transaction mode, in which an explicit `BEGIN IMMEDIATE` raises `cannot start a transaction within a transaction` once any statement has opened one, and trivial single-statement tests still pass so the defect hides. Set `row_factory` to `sqlite3.Row`, then run `PRAGMA journal_mode=WAL` and `PRAGMA busy_timeout=5000` on every open. Both PRAGMAs go on every open even though `journal_mode` persists in the file, because `busy_timeout` is per-connection and would otherwise silently revert to zero — state that in the docstring, as it is the single easiest thing to "optimize" away. One connection per operation, not a shared long-lived connection behind a lock: a shared connection would serialize every read behind every write and discard the concurrency WAL exists to provide, and connection-per-operation also sidesteps `check_same_thread` because `asyncio.to_thread` hands work to arbitrary executor threads.

`writing(conn)` is a `@contextmanager` that executes `BEGIN IMMEDIATE`, yields, executes `ROLLBACK` and re-raises on exception, and executes `COMMIT` on normal exit (D-05). It re-raises; it does not swallow. Reads use a plain autocommit connection with no explicit transaction, because under WAL a reader already sees a consistent snapshot and wrapping reads would serialize readers behind writers for nothing. Do not add a retry-on-`OperationalError` loop: `PRAGMA busy_timeout` is SQLite's own busy handler with internal back-off, and a manual retry loop is both defensive programming and a defeat of D-04's diagnostic intent. The 5000 ms value is chosen to be long enough to absorb snapshot-versus-trade contention and short enough that a genuine locking problem surfaces as a visible error rather than a request that appears to hang.

`ensure_initialized(path)` (D-08) is idempotent and guarded by a module-level flag keyed on the resolved path plus a `threading.Lock`, so it runs once per path no matter how many executor threads reach it. It creates the parent directory if needed, opens a connection, runs `apply_schema`, and then — inside a single `writing()` transaction — checks `is_fresh_database` and calls `seed_fresh` only when it is True. Triggering initialization from the connection helper rather than from lifespan startup is what makes it lazy and what makes it impossible for a future call site to forget: request handlers and Phase 3's snapshot background task both go through the same door. Log initialization once at info level with `%s` lazy formatting.

`get_db_path(request)` is the FastAPI dependency (D-06) returning `request.app.state.db_path`. No module-level connection or path singleton — the same rule CORE-07 applies to `PriceCache` — because tests override exactly this one dependency.

`run_db(path, fn, *args)` is the single event-loop offload seam (D-02, CORE-10): an `async def` whose inner sync callable runs `ensure_initialized(path)`, opens `connect(path)` and returns `fn(conn, *args)`, all handed to `asyncio.to_thread`. Query functions stay plain `def` taking the connection first, so pytest calls them directly with no event loop and there is exactly one place to audit for CORE-10 compliance. Carry a one-line inline comment justifying the offload, matching `massive_client.py`'s precedent.
