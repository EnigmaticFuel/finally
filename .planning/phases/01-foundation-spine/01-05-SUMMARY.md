### Flake characterization (SETUP-06 prohibition: do not dismiss a regression as the flake)

After the gate passed, the flake was exercised deliberately to record its signature rather than assumed. Three isolated runs of the single node:

1. **FAILED** — `assert 3 > (1 + 2)`; the simulator produced exactly 3 ticks where the test needs more than 3
2. **PASSED** (0.11s)
3. **PASSED** (0.09s)

Not reproducible, therefore the known flake and not a regression. The failure mode is exactly the documented one: at `update_interval=0.01` over an `asyncio.sleep(0.05)` window, the expected tick count is ~5 but Windows' ~15.6 ms default timer granularity puts the realistic floor near 3, and the assertion needs 4. It misses by one tick.

**Correction to the prior characterization.** The phase handoff warned against calling this "load-sensitive," and this run is direct evidence for that warning: the test **passed** inside the 243-test full suite and **failed** when run entirely alone. Load is not the variable. It is timer granularity, and an isolated run is if anything the more hostile environment because there is no concurrent activity keeping the event loop warm.

## Decisions Made

- **Generated, not hand-written.** The rewrite ran `ensure_initialized` against the repo-root path via a one-off `uv run` script, so `apply_schema` + `is_fresh_database` + `seed_fresh` executed in exactly the composition the running application uses.
- **Explicit WAL checkpoint.** `connect()` sets `journal_mode=WAL`, so generation leaves `-wal`/`-shm` sidecars. `PRAGMA wal_checkpoint(TRUNCATE)` folded all content into the main file and both sidecars were deleted before staging. Plan 01-04's ignore rules would have kept them out of the commit anyway, but a database committed with pending WAL content is a database whose committed bytes do not carry the seed.
- **Task 4 produced no commit.** It is a read-only gate over an explicitly frozen directory. Committing anything for it would have meant editing something it is forbidden to edit.
