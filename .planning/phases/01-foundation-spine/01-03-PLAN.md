<objective>
Land every SQLite query function the rest of the project calls, and prove the write path holds under genuine concurrency.

Purpose: the roadmap front-loads the whole query surface into this phase on purpose. Phase 3's portfolio work and its watchlist work are otherwise two agents editing one `queries.py` in the same wave, and `execute_trade` needs `add_watchlist_ticker` for its auto-add rule — so a watchlist function deferred to the watchlist plan would block the portfolio plan. Building them together here removes that collision entirely. The concurrency test then proves the layer beneath them: a snapshot write and a trade write happening at the same time must not produce `database is locked`, and must not lose an update either.

Output: `backend/app/db/queries.py` complete, its mirroring test module, the threaded contention proof, and `main.py` wired to the canonical ticker list.
</objective>

  <action>
Create `backend/tests/db/test_concurrency.py`, the direct proof of Phase 1 success criterion 3. Nothing in the codebase drives this code concurrently today, so this test is new ground rather than an extension of an existing pattern.

Use a real file database under pytest's `tmp_path`, never an in-memory one: `:memory:` cannot exercise WAL, `busy_timeout` or genuine lock contention, and under connection-per-operation each in-memory connection would get its own empty database, so the test would pass while proving nothing.

The core test drives writer threads through `writing()` against one file database. Each writer performs a read-modify-write sequence — read `cash_balance` through `get_profile`, add a fixed increment, write it back through `update_cash_balance` — inside a single `writing()` block, so two writers interleaving would produce a lost update rather than merely an error. Run several writer threads across enough iterations to force real contention, and run reader threads concurrently that open plain autocommit connections and read the profile, proving readers are not blocked out. Collect every exception raised in every thread into a shared list rather than letting a thread die silently.

Assert three things, all of which must hold: no thread raised any exception, and specifically zero `sqlite3.OperationalError`; the number of committed writes equals the number attempted; and the final `cash_balance` equals the starting balance plus the increment times the number of committed writes. That third assertion is the one that matters most — zero errors alone would also be satisfied by a design that silently loses updates, and the equality is what proves `BEGIN IMMEDIATE` genuinely serialized the read-modify-write sequences.

Add a second test mixing the two write shapes this phase actually cares about: one group of threads appending through `insert_snapshot` and another appending through `insert_trade`, concurrently, against the same database. Assert zero exceptions and that both row counts equal what was attempted. This is the snapshot-versus-trade collision at the query layer; the realistic version driven by Phase 3's 30-second background task and a real `execute_trade` belongs to Phase 3, once both callers exist.

Add a third, small test asserting the mechanism rather than the outcome: open a connection through `connect()`, hold a `BEGIN IMMEDIATE` write lock on it, and from another thread open a second connection and complete a short write. The second write must succeed once the first releases, within the busy timeout, rather than raising immediately — which is what proves the timeout is doing the waiting rather than a retry loop somewhere.

Keep the total runtime short enough to stay inside the suite's few-second budget; the sampling contract for this phase is a five-second maximum feedback latency.
